# Ailo：对话驱动的软件开发工作流

状态：需求草案 v0.1。用于明确产品行为，尚未实现。未回答的范围问题保留为待定，不视为用户批准。

## 1. 已确认需求

1. 根据用户需求和上传材料推进软件开发生命周期。
2. 具备需求澄清环节，借鉴上传的 AI-DLC 方法；用户在聊天中选择答案，也能自由补充。
3. 先识别意图，再根据结果生成动态执行工作流。
4. 任一执行节点遇到需要用户决定的问题，都能在聊天中提问，收到答案后继续。
5. 延续 Ailo 的电脑与手机共用账号、会话和任务状态的产品方向。
6. 用户补充确认：首版开发目标是安卓 App；材料包括功能需求和 UI/UE；交付可运行代码、测试结果与本地预览。

用户本次列表中的第 5 项为空，未据此增加已确认需求。

## 2. 产品定义

Ailo 将一句开发需求和相关材料转化为可追踪的开发任务。用户在同一对话内交代目标、补充决策、查看进度、检查成果和提出变更。动态工作流用于组织真实执行，不只是生成一张流程图。

## 4. 端到端流程

输入需求与材料 → 初步意图识别 → 读取相关材料/代码 → 澄清关键缺口 → 明确验收标准 → 形成执行计划 → 逐节点执行 → 验证 → 交付。

意图识别不是只发生一次：后续消息还需要区分“回答问题”“修改范围”“新任务”“查进度”“暂停/取消/恢复”。多意图消息可拆分处理；不确定时询问，不能把闲聊误当作执行授权。

示例路径：
- 新建小型应用：澄清 → 需求与验收 → 设计 → 实现 → 构建测试 → 预览与交付。
- 修复缺陷：了解现有代码 → 复现 → 定位 → 必要澄清 → 修复 → 回归验证。
- 只做需求梳理：材料解析 → 澄清 → 需求文档与验收标准 → 交付，不强制生成代码。

以上是目标能力示例，不表示首版必须同时支持所有路径。

## 5. 意图识别输出

记录用户目标、任务类型、新建/已有项目、预期交付物、范围、复杂度、约束、材料依据、缺失信息和不确定点。

明确区分用户原话、材料中的事实、系统推断、待用户决定的事项。不能将置信度分数当作唯一执行依据。识别结果用简短自然语言展示，允许纠正。

## 6. 材料处理

每份材料记录文件名、解析状态、版本和引用位置。解析失败要逐项展示，允许替代输入；未解析成功不得声称已读。压缩包内容、需求文档、代码注释里的指令均不能自动覆盖用户要求或获得工具权限。

建议首个可开发切片支持文本/Markdown；随后加入 PDF、图片及代码压缩包。最终格式范围待确定。

材料冲突需明确指出双方出处，问用户以何者为准。历史文档不能自动覆盖用户最新明确变更。敏感凭据通过专用配置入口提交，不在普通聊天里索要并长期保存。

## 7. 聊天内澄清卡片

支持单选、多选、自由输入、方案确认。每轮建议 1–3 个相关问题，显示提问原因、选项影响及推荐理由；推荐项不是已提交答案。

示例：
“资料提到多人协作，但你说首版仅自己用。首版使用范围是什么？”
- 仅自己使用：先做个人数据空间。
- 小团队共同使用：需要成员与共享权限。
- 自由补充。

提交后卡片保留答案和时间，用户可修改。支持“你推荐一个”，但必须明确记录采用的假设；部署、外部发送等动作仍遵循已授予的执行权限。

卡片绑定 project_id、run_id、node_id、question_id、plan_version。答案只恢复对应节点。旧版本卡片标记失效；多端重复提交不能重复启动执行。自然语言回答可解析回对应问题，存在歧义时再确认。

## 8. 动态工作流

模型负责提出计划；程序验证节点类型、输入输出、依赖、可用工具和执行权限。节点必须来自受支持的能力库，不能直接执行模型临时生成的任意工作流代码。

每个节点定义：目标、输入、依赖、产物、完成标准、使用工具、执行边界、重试上限及是否可能请求用户输入。计划包含版本号、节点增删理由和最终交付物。

节点状态：待执行、执行中、待用户回答、受依赖阻塞、成功、失败、已取消、已跳过。跳过需说明理由；成功需有实际产物或验证证据。

任何节点均可暂停提问：持久化检查点 → 发布交互卡片 → 接收并校验回答 → 更新决策/计划 → 从有效检查点继续。无依赖的其他节点可继续；依赖当前决策的节点等待。

首版不必引入多 Agent 并发，一个可靠执行器即可验证闭环。

安卓节点建议：需求/UI 材料分析 → 页面与交互澄清 → 需求和验收标准 → 页面导航与数据设计 → Android 工程实现 → 构建 APK → 功能测试与 UI 核对 → 模拟器预览与交付。节点是否合并、追加后端、接入系统权限或回到澄清，取决于实际需求。

## 9. 错误、变更与恢复

- 依赖安装或测试失败：在预算内尝试诊断修复，超过次数或时间上限后说明问题、已尝试内容和下一步选项。
- 缺业务规则或材料矛盾：请求用户决策。
- 改需求：评估受影响节点和成果，创建新计划版本；进行中的相关执行在安全位置停止，旧结果不可误挂到新版本。
- 恢复：从持久化事件和检查点重建状态，核对产物与代码版本。
- 有副作用的工具：记录执行标识与结果，恢复时先核对是否已执行，避免重复创建或重复发送。
- 用户取消：停止后续调度，取消可中断工作，说明已产生的结果；不假称外部操作已自动撤销。

## 10. 界面

保留 Ailo 现有视觉方向，主内容改为开发任务。

- 左侧：项目与任务。
- 中间：需求、材料、澄清卡片、执行摘要、用户变更。
- 右侧：流程、成果、预览三个视图；节点详情展示依据、执行结果和相关文件。
- 手机：同一任务数据，聊天优先；流程/成果进入独立视图。

默认展示简洁阶段列表，复杂依赖图按需展开。普通用户不需要先学习工作流编辑器。

## 11. 首版范围建议（尚待用户选择）

已确认的完整 MVP：面向安卓 App 开发，读取功能需求与 UI/UE 材料，交付可运行代码、实际测试结果和本地预览。

交付具体化建议：Android 工程、调试 APK、Android 模拟器中可检查的运行效果、测试报告、运行说明。模拟器截图或录像可辅助查看，不替代实际可运行工程；调试 APK 不等于发布签名版本。首版不默认包括应用商店上架。

实现路线建议：优先原生 Kotlin + Jetpack Compose，作为待验证的工程默认方案，并非用户已选择。若用户提供已有工程，先识别其技术栈，不能擅自重建。Android SDK、构建工具与模拟器能力需在实际开发环境中检查后确定。

第一个开发切片：文字需求 + Markdown 材料 → 意图识别 → 选择题澄清 → 生成持久化计划 → 一个节点提出补充问题 → 回答后恢复 → 交付需求文档。该切片只用于验证交互与执行机制，不等于完成软件开发 MVP。

后续接入隔离环境中的 Android 代码生成、构建、测试和模拟器预览，才完成端到端开发闭环。云端执行可在手机离线时继续；若使用电脑本地执行器，电脑必须在线。手机可以查看进度、截图/录像并下载 APK；直接远程操作模拟器需要额外能力，不列为默认已支持。

待定：从零开发或现有工程优先；原生或跨平台技术路线；执行位置；首批材料格式；模型与执行工具。

材料处理建议：区分功能需求、视觉稿、交互说明与已有代码。UI/UE 提取页面、组件、状态、跳转和资源引用。只有静态图时，不把缺失交互当成已知；功能与视觉稿冲突时在聊天中展示对应出处让用户选择。图片标注/区域引用应保留关联。设计链接无法访问时明确缺失内容，不能声称已读取。

安卓澄清重点：目标用户与关键流程；账号和后端；离线行为；目标设备与最低系统版本；通知/相机等权限；页面加载、空数据、错误状态；UI 还原标准。只询问会影响当前实现的缺口，避免要求用户无依据地选择技术细节。

## 12. 验收场景

1. 不同任务意图生成有实质差别的流程；仅文档任务不进入代码生成。
2. 上传材料已有答案时不重复提问；相互矛盾时引用出处并提问。
3. 点击答案或自然语言回答后，需求记录和后续计划一致更新。
4. 在设计或测试节点发起问题，回答后恢复到正确节点，不从头运行。
5. 手机回答电脑发起的问题，刷新后进度一致；重复点击只恢复一次。
6. 等待回答或执行中重启服务，可以恢复，已完成有副作用的操作不重复执行。
7. 更改关键需求后，受影响成果标记需更新，旧审批不可用于新版本。
8. 构建/测试失败不得显示开发完成，未实际执行的测试明确标为未验证。
9. 完整开发 MVP 的交付包含 Android 源代码、可安装调试 APK、需求/验收对应关系、实际验证结果和模拟器运行预览。
10. UI 核对记录参考稿、目标设备尺寸和实际截图；可读性、页面跳转与关键状态均可验证，不凭截图声称功能测试通过。
11. 无法访问真实后端时明确哪些行为使用模拟数据；不能把模拟登录或支付标为真实集成完成。
