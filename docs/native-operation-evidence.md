# 原生文件过程证据

`operation` 是一个有界的验收依据，用于用户明确要求的完整文本读取、一次 `write_file`、再次完整读取。它复用原要求的 `evidenceBinding`，保留原 ID、文字、类型和文件范围；不是通用操作成功声明，也不能代替网页行为或视觉验收。

`before` 证明归档中的初始读取；`effect` 核对原 `write_file` 的结果或原 actionId 已恢复的目标效果；`after` 核对真实后读。三种阶段共用同一条链。历史初始值不会被解释成当前文件内容，所有通过记录同时依赖当前文件仍等于 after 的 SHA-256。

## 可信来源与边界

来源必须是已纳入计划的完整纯文字用户输入，原文与接收哈希一致。引用的 `sourceQuote` 只用来定位，完整原指令也参与校验。当前入口只接受无歧义的正向文件过程语法：同一路径、明确的初始及目标完整字面值、限定到 `write_file` 动作自身的“一次”，以及后读。允许当前隔离目录的明确操作前缀、输出核对凭证和未知结果不重放等安全语句。

示例、分析或禁止执行的上下文不能通过摘取其中一步取得证明资格；其他路径、值的数字子串、反向值、两次写入、含糊的代词和附加业务义务都不能变成同一纯文件过程。未支持的自由表述、截断原文或带附件消息不会跳过来源校验。组合业务要求继续保持原要求，不能用本入口吞掉其中尚未证明的功能。

仅接受当前任务、当前 execution 中独立归档的直接 `read_file` 完整回执。offset 必须为 0、next 为 null，正文、总长度、SHA-256、原事件与原 actionId 必须一致，正文最多 4000 字符。批量子读、部分分页、模型自述和任意命令输出不属于该入口。

原生 action journal 必须具有严格读取、写入、后读顺序。写入须有唯一原 actionId 与 expectedHash；正常写入要有原 native 成功回执。结果未知时，必须先由原 actionId 的 `action_recovered` 核对并有实际后读，不能重新写入。其他文件可以用 `write_file` 生成凭证；同路径编辑、额外写入、或窗口内任何可能隐藏中间修改的命令/构建都会拒绝，不能拿净 fileChanges 为空声称没有修改。

通过记录保存前后独立归档、原 action 核心字段、效果事件及来源的摘要，后续新鲜度检查重新核对这些字节和全部普通 sources 依赖。当前 after 文件变化会失效；候选恢复后必须取得新的真实完整后读。无关未知远端操作不会被此过程清账，任务完成仍须先处理未知结果。

## 接入与故障用例

`nativeFileOperations` 只提供有界真实 ID 候选，不代表通过。技术纠正先在原要求补 `evidenceBinding.kind=operation`，提供 phase、path、beforeEvidenceId、原 actionId、afterEvidenceId、beforeText、afterText、sourceInputId 和 sourceQuote，再用对应 phase 的完整回执或 actionId 核验。把 native 读取错当 observation 时，走原有请求纠正通道，不产生产品修复目标。

固定场景 `native-operation-evidence` 保留真实 0→1 故障，并以不同路径和 7→9 的实际 runner 复现，覆盖未知写入回执丢失、真实用户续跑、完整新后读推进、来源与阶段/路径/次数错配、隐藏修改和旧 kind 纠正等边界。测试不调用用户模型。离线通过不能证明公司模型已学会选择此依据，也不改变已冻结的真实对照结果。
